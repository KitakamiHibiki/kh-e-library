# kh e-library 软件更新设计方案

## 1. 概述

本文档详细描述 kh e-library（以下简称"本软件"）的更新机制设计，涵盖版本管理、更新模式、更新流程、回滚策略及数据迁移方案。本软件采用 Go 后端 + Vue 前端的单机部署架构，后端使用 SQLite 作为数据库，本地文件系统存储图书文件。

---

## 2. 版本管理

### 2.1 版本号规范

采用语义化版本号（Semantic Versioning 2.0.0）：

```
MAJOR.MINOR.PATCH[-PRERELEASE]
```

| 字段 | 含义 | 示例 |
|------|------|------|
| MAJOR | 不兼容的 API 变更 | 1.0.0 → 2.0.0 |
| MINOR | 向后兼容的功能新增 | 1.0.0 → 1.1.0 |
| PATCH | 向后兼容的 Bug 修复 | 1.0.0 → 1.0.1 |
| PRERELEASE | 预发布标识 | 1.1.0-beta.1 |

### 2.2 版本信息存储

**后端**：通过 `ldflags` 在编译时注入版本号：

```bash
go build -ldflags "-X main.Version=v1.2.3" ./cmd/server
```

当前实现在 `backend/cmd/server/main.go` 第 27 行：
```go
var Version = "dev"
```

**前端**：通过 `.env` 文件或 Vite 构建时注入：
```
VITE_APP_VERSION=v1.2.3
```

### 2.3 数据库 Schema 版本

在 `settings` 表中维护一个 `schema.version` 键，记录当前数据库结构版本号。每次数据库结构变更时递增。

| 设置键 | 示例值 | 说明 |
|--------|--------|------|
| `schema.version` | `3` | 当前数据库 Schema 版本 |

## 3. 更新模式

### 3.1 手动更新（当前模式）

当前版本（v0.x）采用手动更新方式：

1. 用户下载新版本发布包
2. 停止当前运行的服务
3. 替换可执行文件和前端静态资源
4. 重启服务，服务自动执行数据库迁移

**适用场景**：个人部署、小规模使用。

### 3.2 半自动更新（短期目标）

在现有手动更新基础上增加版本检查和更新提示：

```
┌─────────────────────────────────┐
│          更新检查流程            │
├─────────────────────────────────┤
│ 1. 定期/启动时访问更新源        │
│ 2. 比对当前版本与最新版本       │
│ 3. 有新版本时在设置页提示       │
│ 4. 用户确认后下载更新包         │
│ 5. 用户手动执行替换和重启       │
└─────────────────────────────────┘
```

**API 设计**：

```
GET /api/v1/system/check-update
Response:
{
  "code": 200,
  "data": {
    "current_version": "v0.1.0",
    "latest_version": "v0.2.0",
    "has_update": true,
    "changelog": "1. 新增书架功能\n2. 修复 EPUB 解析错误\n3. 优化 PDF 阅读体验",
    "download_url": "https://github.com/xxx/releases/v0.2.0",
    "release_date": 1700000000,
    "breaking_changes": false
  }
}
```

### 3.3 自动更新（远期目标）

实现无人值守的自动更新机制：

```
┌──────────────────────────────────────────┐
│            自动更新流程                    │
├──────────────────────────────────────────┤
│ 1. 服务定时检查更新源（默认每24小时）     │
│ 2. 发现新版本后下载更新包到临时目录       │
│ 3. 校验更新包完整性（SHA-256 + 签名）    │
│ 4. 执行预更新检查（磁盘空间、兼容性）     │
│ 5. 备份当前版本（可执行文件 + 数据库）    │
│ 6. 停止服务                              │
│ 7. 替换文件并执行数据库迁移               │
│ 8. 启动新版本                            │
│ 9. 健康检查通过 → 更新完成               │
│    健康检查失败 → 自动回滚                │
└──────────────────────────────────────────┘
```

**更新源配置**（在 `settings` 表中）：

| 设置键 | 默认值 | 说明 |
|--------|--------|------|
| `update.source_url` | `https://api.kitakami-hibiki.dev/e-library` | 更新源地址 |
| `update.auto_check` | `true` | 是否自动检查更新 |
| `update.check_interval` | `86400` | 检查间隔（秒） |
| `update.auto_install` | `false` | 是否自动安装（需用户手动开启） |
| `update.channel` | `stable` | 更新通道：stable / beta |

## 4. 更新包设计

### 4.1 更新包格式

```
e-library-v1.2.3-update.tar.gz
├── manifest.json          # 更新清单
├── server                 # 新版后端可执行文件
├── web/                   # 新版前端静态资源
│   ├── index.html
│   └── assets/
├── migrations/            # 数据库迁移脚本
│   ├── 002_add_column.sql
│   └── 003_new_table.sql
└── checksums.sha256       # 文件校验和
```

**manifest.json 示例**：

```json
{
  "version": "v1.2.3",
  "min_version": "v1.0.0",
  "max_version": "v1.2.2",
  "release_date": "2026-08-07T00:00:00Z",
  "breaking_changes": false,
  "schema_version": 3,
  "min_schema_version": 1,
  "files": [
    {"path": "server", "size": 25000000, "sha256": "abc123..."},
    {"path": "web/index.html", "size": 500, "sha256": "def456..."}
  ],
  "migrations": [
    {"version": 2, "file": "002_add_column.sql", "reversible": true},
    {"version": 3, "file": "003_new_table.sql", "reversible": true}
  ],
  "changelog": {
    "zh-CN": "1. 新增书架功能\n2. 修复 EPUB 解析错误",
    "en": "1. Added shelf feature\n2. Fixed EPUB parsing error"
  }
}
```

### 4.2 增量更新 vs 全量更新

| 维度 | 全量更新 | 增量更新 |
|------|----------|----------|
| 包大小 | 较大（含完整文件） | 较小（仅差异部分） |
| 实现复杂度 | 低 | 高（需二进制 diff 算法） |
| 可靠性 | 高 | 中（依赖基础版本准确） |
| 适用场景 | 当前阶段 | 大规模部署时 |

**当前策略**：采用全量更新，简化实现并提高可靠性。当发布包体积成为瓶颈时再引入增量更新。

## 5. 更新流程详细设计

### 5.1 预更新检查

更新前必须执行以下检查，任一失败则中止更新：

```go
type PreCheckResult struct {
    CanUpdate     bool     `json:"can_update"`
    Blockers      []string `json:"blockers,omitempty"`
    Warnings      []string `json:"warnings,omitempty"`
    DiskSpaceMB   int64    `json:"disk_space_mb"`
    RequiredSpaceMB int64  `json:"required_space_mb"`
}
```

| 检查项 | 条件 | 失败处理 |
|--------|------|----------|
| 版本兼容性 | 当前版本在 min_version ~ max_version 范围内 | 阻止更新 |
| Schema 兼容性 | 当前 schema_version ≥ min_schema_version | 阻止更新 |
| 磁盘空间 | 可用空间 ≥ 更新包大小 × 3 | 阻止更新 |
| 处理中任务 | 无 book_status=processing 的书籍 | 警告，可继续 |
| 数据库备份 | 备份文件可写入 | 阻止更新 |

### 5.2 备份策略

更新前自动创建备份：

```
data/
├── .backup/
│   ├── v0.1.0_20260807/           # 备份目录
│   │   ├── e-library.db           # 数据库备份
│   │   ├── server                 # 旧版可执行文件
│   │   └── web/                   # 旧版前端资源
│   └── v0.1.0_20260807.meta.json  # 备份元数据
```

**备份元数据**：

```json
{
  "backup_version": "v0.1.0",
  "backup_time": "2026-08-07T12:00:00Z",
  "schema_version": 2,
  "db_size": 1048576,
  "files_count": 15,
  "checksum": "sha256:abc123..."
}
```

**保留策略**：
- 保留最近 3 个版本的备份
- 超过 30 天的备份自动清理
- 备份总大小上限：500MB

### 5.3 更新执行流程

```
┌──────────────────────────────────────────────────────┐
│                    更新执行步骤                        │
├───────┬──────────────────────────────────────────────┤
│ Step 1│ 下载更新包并校验 SHA-256                      │
│ Step 2│ 解压更新包到临时目录                          │
│ Step 3│ 执行预更新检查                               │
│ Step 4│ 创建当前版本备份                             │
│ Step 5│ 进入 drain 模式（拒绝新请求，返回 503）      │
│ Step 6│ 等待异步处理完成（最长 5 分钟）              │
│ Step 7│ 关闭 HTTP 服务（等待在途请求，最长 10 秒）  │
│ Step 8│ 关闭数据库连接                              │
│ Step 9│ 执行数据库迁移                              │
│ Step 10│ 替换后端可执行文件                          │
│ Step 11│ 替换前端静态资源                            │
│ Step 12│ 启动新版本服务                              │
│ Step 13│ 健康检查（/health 接口，重试 3 次）         │
│ Step 14│ 检查通过 → 更新成功                         │
│        │ 检查失败 → 执行回滚                         │
└───────┴──────────────────────────────────────────────┘
```

### 5.4 回滚策略

| 触发条件 | 回滚范围 | 操作 |
|----------|----------|------|
| 数据库迁移失败 | 全量回滚 | 恢复数据库备份 + 旧版文件 |
| 新版本启动失败 | 全量回滚 | 恢复旧版文件（数据库迁移需反向） |
| 健康检查失败 | 全量回滚 | 同上 |
| 迁移成功但新版本运行异常 | 手动回滚 | 用户在设置页触发回滚 |

**回滚流程**：

1. 停止当前服务
2. 从备份恢复数据库文件
3. 从备份恢复旧版可执行文件
4. 从备份恢复旧版前端资源
5. 启动旧版本服务
6. 验证健康检查

## 7. 前端更新策略

### 7.1 静态资源更新

前端构建产物存储在 `backend/web/` 目录，随 Go 二进制一起通过 `embed.FS` 嵌入。更新后端即可同时更新前端。

### 7.2 缓存失效

前端资源文件名包含内容哈希（Vite 默认行为，如 `index-DZGYo6e6.js`），更新后文件名变化自动使浏览器缓存失效，无需额外处理。

### 7.3 版本展示

在设置页面底部展示当前软件版本号，便于用户确认更新状态：

```
kh e-library v1.2.3
```

## 8. 安全设计

### 8.1 更新包签名

使用 Ed25519 数字签名确保更新包未被篡改：

1. 发布时用私钥对 `checksums.sha256` 签名
2. 客户端用内置公钥验证签名
3. 签名验证失败则拒绝更新

### 8.2 传输安全

更新包下载强制使用 HTTPS。

### 8.3 权限控制

- 更新检查 API 不需要认证（只读操作）
- 执行更新操作需要管理员确认（手动模式下由用户操作，自动模式下需在设置页授权）
